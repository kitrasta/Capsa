# Capsa: стабилизация текстового MVP и production-деплой

Дата: 2026-11-02
Статус: на утверждении

## 1. Замысел и причина

Выпустить небольшой, быстрый и надёжный Matrix-клиент для ежедневной текстовой переписки. Сначала довести существующую основу до production-качества и развернуть её, затем развивать продукт по результатам реального использования.

Главная ценность MVP — не количество функций, а отсутствие потерянных сообщений, сломанных сессий, скачков таймлайна, зависаний и непонятных состояний интерфейса.

## 2. Что уже существует

Capsa использует React 19, TypeScript, Vite, CSS Modules и `matrix-js-sdk`. Уже реализованы вход, хранение сессии, lifecycle клиента, IndexedDB, Rust Crypto/E2EE, восстановление шифрования, список комнат, создание чатов, таймлайн, история, отправка сообщений, ответы, правки, реакции, черновики, typing/read receipts и адаптивная двухпанельная раскладка.

На момент проектирования проходят 174 теста, ESLint и production-сборка. Сборка выдаёт предупреждение о большом основном JS-бандле; Rust Crypto WASM также существенно влияет на объём загрузки.

VPS уже содержит Docker Compose-инфраструктуру с Synapse, PostgreSQL и Caddy. Настроены HTTPS и имена:

- `capsachat.org` — Matrix discovery и корневой сайт;
- `matrix.capsachat.org` — homeserver;
- `web.capsachat.org` — будущий web-клиент;
- `/srv/capsa/web` — каталог, который Caddy отдаёт для web-клиента.

## 3. Цели MVP

### Пользовательские сценарии

Пользователь должен иметь возможность:

1. Войти в существующий аккаунт на homeserver'е Capsa и восстановить сессию после перезагрузки.
2. Увидеть актуальный список личных и групповых чатов, последнее сообщение и непрочитанные.
3. Создать личный или групповой чат и открыть существующий по прямой ссылке.
4. Читать текстовую историю с корректной пагинацией и сохранением позиции чтения.
5. Отправлять и получать сообщения, отвечать, редактировать свои сообщения и ставить реакции.
6. Видеть состояния отправки, typing и read receipts; сохранять черновик отдельно для каждой комнаты.
7. Использовать зашифрованные комнаты и пройти существующий сценарий восстановления шифрования.
8. Работать в современном desktop- и mobile-браузере без потери основных сценариев.
9. Понимать, когда идёт загрузка, отсутствует сеть, комната недоступна или сессия истекла.

### Технические цели

- Устранить подтверждённые ошибки критичных сценариев до релиза.
- Измерить производительность production-сборки до оптимизаций и после них.
- Убрать лишние ререндеры, повторные подписки, утечки слушателей и дорогие пересчёты в горячих путях.
- Обеспечить управляемую загрузку JS/WASM и кеширование статических ресурсов.
- Развернуть статический SPA на существующем VPS с возможностью отката.
- Задокументировать сборку, конфигурацию, деплой, проверку релиза и известные ограничения MVP.

## 4. Не входит в MVP

- Отправка и полноценное отображение фотографий, видео, файлов, голосовых и стикеров.
- Звонки.
- Поиск по содержимому сообщений.
- Push-уведомления и расширенные настройки уведомлений.
- Вход через произвольный homeserver и выбор сервера в UI.
- Публичная регистрация и управление аккаунтом вне существующих возможностей приложения.
- Редизайн, новая дизайн-система или переписывание UI под Cinny.
- Смена фреймворка, Matrix SDK или архитектуры проекта.
- Новые функции, не требующиеся для перечисленных сценариев.

Наличие заглушек для будущих разделов не является причиной реализовывать эти разделы перед релизом.

## 5. Анти-цели

MVP не должен достигаться ценой:

- глобального рефакторинга без измеримой проблемы;
- преждевременного внедрения state-manager'а или новой библиотеки;
- оптимизаций без профиля и сравнения «до/после»;
- скрытия ошибок за бесконечными loader'ами или `console.error`;
- моков вместо проверки настоящего Matrix-сервера;
- копирования кода Cinny;
- коммита паролей, access token'ов, recovery key'ей или содержимого реальных `.env`;
- изменения Synapse/PostgreSQL без отдельной подтверждённой причины и резервной копии соответствующей конфигурации.

## 6. Ограничения и принятые решения

- MVP работает только с `https://matrix.capsachat.org`; server name — `capsachat.org`.
- Адреса задаются при сборке через существующие `VITE_MATRIX_HOMESERVER_URL` и `VITE_MATRIX_SERVER_NAME`.
- Приложение остаётся статическим SPA; service worker/PWA и серверный рендеринг в MVP не добавляются.
- Используется существующий Caddy. SPA fallback, `index.html: no-cache` и долгоживущий immutable-cache для hashed assets должны сохраняться.
- Matrix discovery и маршруты homeserver'а нельзя ломать при деплое клиента.
- Целевые браузеры — актуальные Chrome/Chromium, Firefox и Safari; legacy-браузеры не поддерживаются. Это решение исполнителя, а не отдельное требование пользователя.
- Основой служат текущие feature-oriented структура и публичный Matrix API из `src/shared/lib/matrix/`; менять их без необходимости не нужно.
- Выбор лицензии необходим перед публикации исходного кода, но не блокирует технический деплой MVP.

## 7. Рассмотренные подходы

### A. Стабилизация существующего приложения, затем деплой — выбран

Заморозить функции, установить baseline, последовательно проверить надёжность и производительность, исправить release blockers, развернуть и провести production smoke test.

Плюсы: меньше риска для данных и первых пользователей; сохраняется работающая архитектура; объём изменений ограничен фактическими проблемами.
Минусы: первый публичный адрес появится позже, чем при немедленном деплое.

### B. Немедленный деплой текущего состояния, исправления после обратной связи

Плюсы: самый быстрый выход и ранняя обратная связь.
Минусы: пользователи станут тестировщиками критичных сценариев E2EE, сессий и синхронизации; сложнее отличить проблемы клиента от серверных и сетевых.

Выбран подход A, поскольку пользователь явно приоритизировал быстрый и стабильный MVP.

Полный рефакторинг перед релизом отклонён: текущая кодовая база уже работает и покрыта тестами, а такой рефакторинг увеличил бы риск без доказанной пользы.

## 8. Этапы работ

### Этап 1. Baseline и карта release blockers

- Зафиксировать результаты test/lint/build, размеры assets и сценарии ручной проверки.
- Проверить production build в браузере, а не только dev server.
- Подготовить воспроизводимые тестовые данные: аккаунт с большим количеством комнат и комнату с длинной историей, без использования переписки реальных пользователей.
- Профилировать первый запуск, повторный запуск с кешем, переключение комнат, набор текста, получение сообщения, прокрутку и пагинацию.
- Составить список подтверждённых проблем с приоритетом; не начинать оптимизации только по предположениям.

### Этап 2. Надёжность критичных сценариев

- Проверить граничные случаи lifecycle: повторный старт, logout во время запуска, истёкший токен, ошибка инициализации crypto, восстановление после offline.
- Проверить гонки поиска, переключения комнат, загрузки истории, отправки и расшифровки.
- Проверить отсутствие потери текста/ответа при неудачной отправке и корректность read markers.
- Устранить подтверждённые ошибки небольшими изменениями с регрессионными тестами.
- Сделать видимыми actionable-состояния ошибок там, где сейчас пользователь не понимает дальнейшее действие.

### Этап 3. Производительность и объём загрузки

- Сначала устранить измеренные горячие места в списке комнат и таймлайне.
- Проверить необходимость виртуализации длинной ленты по профилю; внедрять её только при доказанной необходимости и с сохранением пагинации, ответов и scroll anchoring.
- Разделить маршруты/тяжёлые подсистемы и отложить необязательную для первого экрана загрузку, если это подтверждается измерениями.
- Проверить загрузку WASM, MIME/HTTPS и поведение при холодном кеше.
- Сравнить показатели с baseline и зафиксировать результат.

Рабочие ориентиры на согласованном тестовом наборе: ввод текста не должен блокироваться ререндером ленты; обычные действия не должны создавать заметных main-thread зависаний; пагинация не должна визуально дёргать чат; повторные переключения комнат не должны накапливать подписки и потребление памяти. Численные показатели и используемое устройство фиксируются вместе с baseline, чтобы не выдумывать недостижимые бюджеты до измерений.

### Этап 4. Release candidate

- Прогнать unit/integration tests, TypeScript, ESLint и production build.
- Провести браузерный smoke test критичных сценариев на реальном homeserver'е с тестовыми аккаунтами.
- Отдельно проверить E2EE между двумя сессиями и восстановление ключей, не выводя секреты в логи.
- Проверить мобильную раскладку, клавиатуру, прямые ссылки и перезагрузку `/chats/:roomId`.
- Обновить README и deployment-инструкции в соответствии с фактическим поведением.

### Этап 5. Деплой и проверка production

- Собрать artifacts локально или в воспроизводимом CI с production-конфигурацией только для homeserver'а Capsa.
- Загрузить release в отдельный каталог, проверить его и переключать опубликованную версию без смешивания assets разных сборок.
- Сохранить предыдущий release для быстрого отката; конкретный механизм переключения выбирается в плане с учётом текущего Caddy mount.
- Не менять рабочие Synapse/PostgreSQL и Matrix discovery без необходимости.
- Проверить HTTPS, SPA fallback, cache headers, WASM, вход, sync и отправку/получение сообщения уже на `web.capsachat.org`.
- Задокументировать версию release и процедуру rollback.

## 9. Критерии готовности

MVP считается готовым, когда:

1. Все автоматические проверки проходят, а новые исправления имеют регрессионные тесты там, где это применимо.
2. Критичные пользовательские сценарии из раздела 3 пройдены против production homeserver'а.
3. Известные release blockers устранены; оставшиеся ограничения явно перечислены и не мешают текстовой переписке.
4. Профилирование не показывает воспроизводимых блокировок основных сценариев на согласованном наборе данных; результаты «до/после» записаны.
5. Длинная история, смена комнат и reconnect не приводят к скачкам, дублированию событий или росту слушателей.
6. Два независимых клиента корректно обмениваются обычными и зашифрованными сообщениями.
7. Production-домен открывается по HTTPS, переживает refresh вложенного маршрута и корректно загружает JS/WASM.
8. Деплой и rollback описаны и проверены; секреты в репозитории и клиентском бандле отсутствуют.

## 10. Что остаётся на усмотрение исполнителя

- Конкретные тестовые данные, инструменты профилирования и численные performance-бюджеты после baseline.
- Нужна ли виртуализация и какой минимальный механизм code splitting оправдан измерениями.
- Точный механизм атомарной публикации releases и rollback в рамках существующего Caddy.
- Небольшие UX-исправления ошибок и loading-состояний без изменения общей стилистики.
- Необходимость CI: для первого релиза допустим документированный локальный build + scripted deploy, если он воспроизводим и безопасен.

Любое расширение функционального объёма сверх раздела 3 требует отдельного согласования и переносится после MVP.
